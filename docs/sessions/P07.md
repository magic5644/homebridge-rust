## Result and interfaces

`bridge_core::config::{AppConfig, load_config, save_config_atomic}` implement
schema version 1, default API `127.0.0.1:8582`, default HAP port `51827`, semantic
validation and rejection of equal API/HAP ports. Port availability is not probed.
Both TaHoma authentication modes remain mutually exclusive; unknown fields and
inline credential fields are rejected. `StopAndReview` remains the only backend.

`AppConfig` and `TahomaConfig` deliberately do not implement `Serialize` or
`Debug`. The explicit atomic writer creates a **private on-disk** JSON document,
including the existing private gateway selection/PIN fields and credential file
references, never credential contents. It is not a public API DTO or public
backup. Future HTTP views must use separate redacted DTOs. The example contains
only invented values; copy it into a 0700 directory with mode 0600 before using
`check`. Relative paths use the process working directory; use absolute paths in
service configuration when the working directory is not fixed.

`bridge_core::secrets::{load_secret, Secret}` reads at most 64 KiB of UTF-8,
nonblank secret text from a local file. `Secret::expose()` is an explicit
connector boundary; `Debug` is redacted and no serialization or Display is
implemented. P11 owns account JSON/token semantics and actual authentication.
Config reads/writes are limited to 1 MiB. Paths containing URLs, symlink
components, parent traversal for actual file access, nonregular files, hard
links, nonprivate files and nonprivate immediate parent directories are rejected.
Existing file/directory permissions are never silently changed. New directories
are 0700 and files 0600. New private parent directories are synchronized.

The writer uses a same-directory exclusive temporary file, writes/synchronizes
it, atomically renames it and synchronizes the containing directory. Failed
writes/renames preserve the old file and temporary cleanup is attempted.
A directory-sync failure **after successful rename** returns a storage error:
the new file may already be visible and its crash durability is unknown. The
caller must inspect/reload rather than assume rollback.

`bridge-server check --config PATH` now validates the schema without opening
referenced secret/CA files, creating directories, connecting, publishing HomeKit
or modifying equipment. It prints only a fixed success message or redacted
`BridgeError`; neither input paths nor parser diagnostics are echoed.

Changed files: core configuration/secrets/export/manifest/contract tests,
server manifest/CLI/tests, lockfile and root `config.example.json`.
Dependencies: no new external crate; existing `serde_json` becomes a runtime
core dependency and server now depends on core.

## Limits and handoff

No remote CI, Linux/QNAP filesystem run, real disk-full filesystem, process-kill
crash test, network, equipment or HomeKit interoperability was performed. The
filesystem code targets Unix (Linux deployment and macOS development). The
application user, administrators and owners of configured ancestor directories
are trusted: std path checks are not a dirfd sandbox against hostile same-user
or ancestor-directory replacement. Filesystem permissions do not protect against
NAS administrators or memory inspection; secret values are not zeroized.

P08 can consume validated `AppConfig`; P11 can load selected local secrets and
must validate mode-specific credential structure, CA/DNS and endpoint identity.
The coordinator owns contract/state/plan reconciliation, review, PR, latest-head
CI, merge and exact-main CI; this report does not claim `done`.
