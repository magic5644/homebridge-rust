## Implemented behavior

One dedicated OS thread owns one SQLite connection and the directory lock. Its
Tokio request queue holds 64 waiting operations; saturation returns `Busy` without
adding an unbounded waiter. Clones share that worker and a 256-event broadcast.
All filesystem/SQLite operations, including open and backup, run on this worker.
Dropping all Store handles closes the queue; already admitted work drains and the
worker releases its lock. Reopening immediately may briefly encounter that lock.

The migration transaction creates `schema_migrations`, `devices`, `hap_ids`,
`commands`, `sessions` and `settings`. Unique source keys and request IDs are
SQL-enforced. Devices are JSON-backed rows; every snapshot change and its durable
revision commit together. Source identities, selected ownership, AIDs and named
IIDs survive rename, inventory ordering/removal, service-key removal and restart.
New devices start in `observe`; absent devices remain unavailable identity records.

Admission validates the current device/capability/ownership/availability and
transactionally returns the existing receipt with `is_new=false` for duplicate
normalized commands. Changed device/command content conflicts. Origin does not
change command identity. Only new admissions can authorize downstream transmission.
`mark_sent` commits the execution ID and `Sent` together. Expired terminal records
can be pruned after 24 hours; the 10,000-record bound rejects new work while live
keys occupy the capacity. Old nonterminal records are preserved rather than
silently evicted. On restart, nonterminal commands become `Unknown`; no network
transmission or replay exists in Store.

Coordinator-approved contract clarifications:

- Integration `false` persists the setting and marks its available devices
  unavailable in the same transaction/revision. Snapshot/integration events follow
  commit. Incoming discovery/updates cannot restore availability while that flag
  remains false. Integration `true` alone does not invent device recovery; fresh
  discovery/updates must restore individual availability. State values and quality
  are preserved; P14 owns staleness policy.
- Trusted tracking callers can resolve `Unknown` to `Succeeded`, `Failed` or
  `Cancelled` using explicit manufacturer evidence. Unknown never returns to
  Accepted/Sent/Running or permits `mark_sent`; duplicate admissions still cannot
  send again. Other terminal outcomes are immutable, with same-value idempotency.

`backup_to` uses SQLite's backup API and requires a new destination. An existing
backup is preserved; a failed copy removes the newly reserved incomplete file.
Store creates its data directory as 0700 and DB/lock/backup files as 0600 on Unix.
Unsafe existing final paths, symlinks, nonregular files and modes are rejected
without chmod. Normalizing trailing separators/dot avoids bypassing the final-path
symlink check. The application user/administrator and existing ancestor directories
remain trusted; hostile concurrent mutation by that user is outside this boundary.
Non-Unix permission enforcement is unsupported and fails closed.
