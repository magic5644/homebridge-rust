## Delivered behavior

`TahomaClient::connect(TahomaConfig, TahomaCredentials)` authenticates using
an actual bounded setup read. Local mode requires the canonical DNS identity
`gateway-{configured_pin}.local`, the configured CA only, and verified Rustls
TLS. An optional resolved IP preserves the DNS URL and SNI. Account mode uses
only explicit SomfyEurope password/refresh OAuth and fixed public endpoints.
It verifies the selected gateway and structurally filters other gateways.
There is no local/cloud/cookie fallback, proxy, redirect, TLS key logging or
automatic request retry. Clients and OAuth sessions are shared across clones.
Idle connections are limited to one per host; every HTTP operation has a
five-second total deadline and every response has a four-MiB incremental bound.
Automatic content decompression is disabled, so encoded content cannot evade
a decoded-size bound; unexpected compressed JSON fails decoding.

The account session renews proactively with a five-second skew under one mutex,
rechecks expiry, accepts refresh rotation, and rejects missing/invalid tokens.
Expired sessions without refresh credentials fail before API transmission.
Authentication rejection never replays consuming event fetches or raw commands.
Credentials and sessions have no Debug or serialization implementation; public
errors contain fixed messages and never format reqwest/serde diagnostic values.
TLS failures and unavailable connections have distinct project error codes.

The required setup, listener registration/fetch/unregistration, raw execution
apply and execution-query routes use verified verbs and individually encoded
path segments. Unknown execution states map to `Unknown`; missing executions
are errors, never proof of success. Unknown event types are retained while
malformed known fields fail. Device events from other gateways are filtered.

`raw_setup()` returns the minimum public `RawTahomaDevice` DTO seam for P12/P13.
`setup()` currently returns metadata, availability, empty capabilities and no
invented state. Typed `apply_raw()` carries profile-encoded action groups and
checks selected-gateway targets; P15 must enforce device ownership, availability,
capabilities and parameters before using it. Semantic `execute` and command
encoding deliberately remain P15 work; there is no fake-success implementation.
No server runtime uses this transport yet.

the public MCP HTTP endpoint. Actual APIs were checked against reqwest 0.13.5
and Rustls 0.23.46 primary source because Context7 Rustls snippets target main.
Pinned official local OpenAPI and PyOverkiz provider/authentication source are
linked in [the implementation design](../integrations/tahoma-client-design.md).

checked with OpenSSL and SHA-256. The public application constants retain their
upstream source and MIT notice in [provenance](../../crates/integration-tahoma/certs/PROVENANCE.md).

Test-first evidence: setup failed against the initial transport stub; metadata
field handling, malformed known events and unavailable/TLS distinction each
failed before their corresponding corrections. The completed suite uses real
Rustls HTTPS connections bound to loopback, a generated fictional CA/key, and
manual DNS resolution. The proxy-variable check runs in an isolated subprocess.
There are 21 new behavior tests: five account unit tests, eleven HTTP contract
tests and five TLS contract tests.

- `cargo test -p integration-tahoma --test http_contract --test tls_contract --locked`.
- `cargo test -p integration-tahoma --test http_contract --test tls_contract --lib --locked`.

## Limits and resumption

No real mDNS, manufacturer login, household secret file, gateway, equipment
command, pairing or deployment was accessed. Actual local certificate chains,
SomfyEurope account compatibility, device payload/profile compatibility and
physical behavior remain unproven. Public-source OAuth evidence is not a
manufacturer stability guarantee. Fixture keys are deliberately public and
must never be installed as production credentials.

P12/P13 can consume the raw DTO seam; P14 can use listener methods; P15 can
supply semantic encoding/admission and use the raw apply route. The coordinator
must review/integrate commits, reconcile contracts/plan/state and verify head
and exact-main CI before marking P11 done. No hardware checkbox is closed here.
